# Conclusiones

- El Sprint 1 permitió al equipo cumplir el objetivo planteado: desarrollar y desplegar en GitHub Pages la Landing Page de Veygo como punto de entrada a la plataforma. Se construyó una interfaz funcional, visualmente coherente y alineada con la propuesta de valor del producto, con las secciones de Hero, segmentación de usuarios, buscador de vehículos, categorías, proceso operativo, vehículos destacados, confianza, testimonios y footer, además de soporte bilingüe (español e inglés) y un diseño adaptable a distintos dispositivos. Quedaron pendientes las secciones de preguntas frecuentes y suscripción a novedades.

- Al tratarse de un Sprint introductorio, el alcance del Sprint 1 se limitó a la capa de presentación, sin lógica de negocio ni integración con servicios. Esto permitió priorizar la calidad de la primera impresión del usuario. La retrospectiva evidenció que se trabajó directamente sobre `main` y sin una convención uniforme de commits, lo que llevó al equipo a adoptar GitFlow y Conventional Commits en el siguiente Sprint.

- En el Sprint 2 se implementó y desplegó en Firebase Hosting la primera versión del Frontend Web Application de Veygo, que cubre 20 historias de usuario (66 story points). El arrendatario puede registrarse, buscar vehículos en un mapa, filtrarlos, reservarlos, guardarlos como favoritos, calificar sus alquileres y comunicarse con el propietario; el propietario puede publicar y gestionar su flota, controlar la disponibilidad, aceptar o rechazar solicitudes y revisar sus métricas, transacciones y calificaciones.

- La organización del código por bounded contexts (IAM, Fleet, Booking, Engagement, Reputation, Payment, Communication, Notification y Dashboard), con capas domain, application, infrastructure y presentation, permitió que cada integrante trabajara su contexto en una rama `feature/*` independiente y lo integrara mediante Pull Requests, aplicando GitFlow. Asimismo, el uso de una Fake API con json-server bajo el prefijo `/api/v1`, desplegada en Render, permitió validar la aplicación con datos persistentes y definir los contratos REST que tendrán los Web Services.

- El Sprint 2 también mostró oportunidades de mejora: la carga de trabajo no se distribuyó de manera equilibrada entre los integrantes y algunos commits no siguieron la convención acordada. Para los siguientes Sprints, el equipo se propone repartir los bounded contexts de forma más equitativa y respetar Conventional Commits en todos los commits.

- Como siguiente paso, el equipo implementará los Web Services en ASP.NET Core con Entity Framework Core y MySQL, documentados con OpenAPI (Swagger), con autenticación mediante JWT y contraseñas cifradas con BCrypt. Luego, reemplazará la Fake API por estos servicios en el Frontend Web Application y completará las secciones pendientes de la Landing Page.
