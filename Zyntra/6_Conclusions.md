# Conclusiones

- El Sprint 1 permitió al equipo cumplir el objetivo planteado: desarrollar y desplegar en GitHub Pages la Landing Page de Veygo como punto de entrada a la plataforma. Se construyó una interfaz funcional, visualmente coherente y alineada con la propuesta de valor del producto, con las secciones de Hero, segmentación de usuarios, buscador de vehículos, categorías, proceso operativo, vehículos destacados, confianza, testimonios y footer, además de soporte bilingüe (español e inglés) y un diseño adaptable a distintos dispositivos. Quedaron pendientes las secciones de preguntas frecuentes y suscripción a novedades.

- Al tratarse de un Sprint introductorio, el alcance del Sprint 1 se limitó a la capa de presentación, sin lógica de negocio ni integración con servicios. Esto permitió priorizar la calidad de la primera impresión del usuario. La retrospectiva evidenció que se trabajó directamente sobre `main` y sin una convención uniforme de commits, lo que llevó al equipo a adoptar GitFlow y Conventional Commits en el siguiente Sprint.

- En el Sprint 2 se implementó y desplegó en Firebase Hosting la primera versión del Frontend Web Application de Veygo, que cubre 20 historias de usuario (66 story points). El arrendatario puede registrarse, buscar vehículos en un mapa, filtrarlos, reservarlos, guardarlos como favoritos, calificar sus alquileres y comunicarse con el propietario; el propietario puede publicar y gestionar su flota, controlar la disponibilidad, aceptar o rechazar solicitudes y revisar sus métricas, transacciones y calificaciones.

- La organización del código por bounded contexts (IAM, Fleet, Booking, Engagement, Reputation, Payment, Communication, Notification y Dashboard), con capas domain, application, infrastructure y presentation, permitió que cada integrante trabajara su contexto en una rama `feature/*` independiente y lo integrara mediante Pull Requests, aplicando GitFlow. Asimismo, el uso de una Fake API con json-server bajo el prefijo `/api/v1`, desplegada en Render, permitió validar la aplicación con datos persistentes y definir los contratos REST que tendrán los Web Services.

- El Sprint 2 también mostró oportunidades de mejora: la carga de trabajo no se distribuyó de manera equilibrada entre los integrantes y algunos commits no siguieron la convención acordada. Para los siguientes Sprints, el equipo se propone repartir los bounded contexts de forma más equitativa y respetar Conventional Commits en todos los commits.

- En el Sprint 3 se implementó y desplegó la primera versión de los Web Services de Veygo como una RESTful API en ASP.NET Core 10, organizada por bounded contexts (Fleet, Booking, Engagement, Reputation, Communication y Notification, junto con un Shared Kernel) y con capas Domain, Application, Infrastructure e Interfaces. La API expone 27 endpoints bajo el prefijo `/api/v1`, documentados con OpenAPI y publicados mediante Scalar, y responde los errores en formato Problem Details en inglés y español.

- La persistencia se implementó con Entity Framework Core y MySQL, gestionando el esquema mediante migraciones y aplicando patrones como Repository, Unit of Work, CQS y eventos de dominio para la comunicación entre contextos (por ejemplo, las notificaciones que se generan al cambiar el estado de una reserva). Los Web Services se desplegaron en Render mediante Docker, con la base de datos en un servicio administrado de MySQL en Aiven y conexión cifrada, sin exponer credenciales en el repositorio.

- El Frontend Web Application se conectó a los Web Services y se publicó una nueva versión en Firebase Hosting: vehículos, disponibilidad, reservas, favoritos, calificaciones, mensajes y notificaciones ya se gestionan desde la API desarrollada por el equipo. La gestión de usuarios se mantuvo en la Fake API, ya que el bounded context IAM se postergó para el siguiente Sprint. Además, se publicó una nueva versión de la Landing Page con los videos About-the-Product y About-the-Team incrustados, el inglés como idioma por defecto y mejoras de accesibilidad.

- Las entrevistas de validación con usuarios de ambos segmentos permitieron identificar seis problemas de usabilidad, arquitectura de información y diseño inclusivo, priorizados según su severidad, que servirán como insumo para las mejoras del siguiente Sprint.

- En cuanto al trabajo en equipo, el desarrollo de los Web Services aplicó GitFlow de forma consistente: cada bounded context se implementó en una rama `feature/*` y se integró mediante Pull Requests. Sin embargo, la participación en el Frontend Web Application y la Landing Page siguió concentrada en pocos integrantes, y no todos los miembros registraron aportes en todos los productos. Para el siguiente Sprint, el equipo se propone asignar tareas en los tres productos a cada integrante desde el Sprint Planning y hacer seguimiento de los aportes durante el Sprint.

- Como siguiente paso, el equipo implementará el bounded context IAM en los Web Services, con autenticación mediante JWT y contraseñas cifradas con BCrypt, para retirar por completo la Fake API del Frontend Web Application. También atenderá los problemas detectados en las evaluaciones heurísticas y completará las secciones pendientes de la Landing Page (preguntas frecuentes y suscripción a novedades).
